Yes. TeX Live's own packaging already reflects most of this ontology, and the current vendoring flattens it. For example, `lib-ctan/latex` is the kernel's TeX Live archive filtered down to four files (`t1enc.def`, `ot1enc.def`, `ansinew.def`, `shortvrb.sty`). So the kernel isn't really vendored: neither `latex.ltx` nor any `.dtx` is there.

I'd use three independent axes, the same pattern as the construct ontology.

**Axis 1: role.** What the file is in the TeX system, and who reads it:

| Role | Read by | Examples | Feeds in PyTeXML |
| --- | --- | --- | --- |
| Engine reference | nothing; it documents the engine itself | `tex.web`, the e-TeX and pdfTeX manuals | the engine primitive core |
| Format kernel | the format build; always present | latex-base `.dtx` files, built into `latex.ltx`; `l3kernel` (expl3) | the kernel binding layer: declarators, the package mechanism, counters, cross-references, sectioning |
| Class | `\documentclass` | article/report/book, amsart, revtex4-2, elsarticle, IEEEtran | class bindings |
| Package | `\usepackage`, `\RequirePackage` | natbib, fancyhdr, geometry, cleveref | package bindings |
| Generic macro package | `\input`, usually through a LaTeX wrapper | pgf's `.code.tex` core, xypic | binding on the wrapper; the generic code is evidence |
| Support file | `\input` by its owning package or class | `.def` drivers and encodings, `.fd`, `.clo`, `.cfg`, `.ldf`; biblatex's `.bbx`/`.cbx` | part of the owner's binding; `.cfg` is a configuration point |
| Data file | `\input` as data | `unicode-math-table.tex`, `dvipsnam.def`, babel's `.ini` locales | table extraction |
| Processor style | an external program, not TeX | `.bst` (BibTeX), `.ist` (makeindex) | style bindings for the bibliography track |
| Venue template | shipped with papers; not in TeX Live | `neurips_2024.sty`, `iclr2026_conference.sty` and its `.bst` | the template registry (ontology O9) |
| Fonts | engine or driver | `.tfm`, `.vf`, `.pfb`, `.map`, `.enc` | out of scope, except encoding tables for slot-to-Unicode maps |

On `.bst`, since you weren't sure: it's a program in BibTeX's own stack language, run by BibTeX, not TeX, and its output is the `.bbl`. We don't run it, any more than we run TeX. It gets read to derive style bindings: entry templates, sorting and labels. There's a useful shortcut. Many styles are generated by custom-bib's makebst from `merlin.mbs`, and the generated file's header lists the options it was built with. That option list is already a declarative description of the style. biblatex's style files are a different case: they're TeX files that biblatex loads, so they're support files of biblatex.

**Axis 2: form.** How a file relates to what actually gets read:
- **Runfile:** what TeX or BibTeX reads. This is authoritative for behavior, and evidence citations point here.
- **Literate source:** `.dtx` and `.ins`, or `.mbs` generators. They carry intent and comments. We keep them as text and never run docstrip.
- **Documentation:** manuals.

TeX Live already splits these into separate archives: `<pkg>.tar.xz` for runfiles, `<pkg>.source.tar.xz` for sources and `<pkg>.doc.tar.xz` for documentation. So vendoring the kernel's `.dtx` files means fetching `latex.source.tar.xz`, with no TeX run involved.

**Axis 3: unit.** What gets pinned versus what gets owned:
- **Acquisition unit:** a TeX Live archive with its revision and checksum. One archive can hold many logical units: `tools` holds array, calc, verbatim and more; `graphics` holds graphicx, color and keyval.
- **Logical unit:** one `\ProvidesPackage`, `\ProvidesClass` or `\ProvidesFile`. This is what bindings own and what local-copy identification hashes.
- **Owner group:** a logical unit plus its support files.
- **Version:** the kernel's version is a LaTeX release (with rollback through `latexrelease`); every package has its own.

**What changes for vendoring:**
1. **Record role, form and logical unit for every member file** in its provenance entry, not just `role: own`.
2. **Vendor the kernel properly:** the full `latex` runfiles including `latex.ltx` and the standard classes, `latex.source` for the `.dtx` files, and `l3kernel`, all pinned to one LaTeX release.
3. **Pull processor styles from the TeX Live packages that ship them:** base BibTeX's plain/alpha/unsrt, natbib's plainnat family, harvard's agsm, and custom-bib's `merlin.mbs` as the generator source.
4. **Give venue templates their own collection,** pinned by banner and hash, with provenance noting the venue kit or the corpus paper where each was first seen.
5. **Vendor the engine reference once,** as specification text for the engine core.

The kernel plus LaTeX's required bundles (amslatex, babel, cyrillic, graphics, psnfss, tools) are available in every install. That makes them a priority tier for binding, not a separate kind.
